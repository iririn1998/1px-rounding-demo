# 1px Rounding Demo

Webアプリケーションで発生する「1pxのずれ」を再現・観察するためのデモです。

`700px` の枠の中に3等分(`1fr 1fr 1fr`)のグリッドを置くだけの単純な構造ですが、ブラウザのズーム率やOSの表示スケールによっては合計幅が枠を1px超え、意図しない横スクロールバーが現れます。

この現象を理解するには、まず **px という単位が一種類ではない** ことを押さえる必要があります。

---

## 1. pxとは何か

「px」と呼ばれるものは、少なくとも3つの異なる概念に分かれます。

| 呼び方 | 別名 | 何を指すか |
| --- | --- | --- |
| CSSピクセル | 論理ピクセル / device-independent pixel | CSSに書く `width: 700px` の px |
| デバイスピクセル | 物理ピクセル | ディスプレイの実際の画素 |
| レイアウト内部単位 | LayoutUnit / app unit | ブラウザが計算に使う内部の細かい単位 |

### 1.1 CSSピクセル(論理ピクセル)

CSSの `px` は「画面の画素1個」ではありません。CSS仕様上は **絶対単位** として定義されており、`1in = 96px` という関係に固定されています。

```
1px = 1/96 inch
```

つまりCSSのpxは、物理的な長さの単位に近い「基準となる見た目の大きさ」です。仕様では **参照ピクセル(reference pixel)** という考え方で、「腕を伸ばした距離(約28インチ)から見たときの1/96インチの視角」と定義されています。

なぜこんな定義かというと、スマートフォンの高精細ディスプレイで `font-size: 16px` が画素1個ずつに対応してしまうと、文字が肉眼で読めないほど小さくなるからです。CSSピクセルを物理画素から切り離すことで、どのデバイスでも「だいたい同じ大きさに見える」ことが保証されます。

**CSSピクセルは小数を取れます。** `width: 233.333px` は正当なCSSであり、`getBoundingClientRect()` も小数を返します。

### 1.2 デバイスピクセル(物理ピクセル)

ディスプレイが実際に発光させる画素です。こちらは **整数でしか存在できません**。画素の半分だけ光らせることはできません。

「フルHD(1920×1080)」のような解像度表記は、このデバイスピクセルの数です。

### 1.3 devicePixelRatio(DPR)

両者をつなぐ倍率が `window.devicePixelRatio` です。

```
デバイスピクセル数 = CSSピクセル数 × devicePixelRatio
```

| 環境 | DPR | 意味 |
| --- | --- | --- |
| 一般的なデスクトップモニタ(スケール100%) | 1 | CSS 1px = 物理 1px |
| Windows 表示スケール 125% | 1.25 | CSS 1px = 物理 1.25px |
| Windows 表示スケール 150% | 1.5 | CSS 1px = 物理 1.5px |
| Mac Retina / 高DPIモニタ | 2 | CSS 1px = 物理 2px |
| 近年のスマートフォン | 2〜4(端数もあり) | 機種依存 |

ブラウザのコンソールで確認できます。

```js
window.devicePixelRatio;
// 1 / 1.25 / 1.5 / 2 など
```

**DPRが整数でない環境(1.25, 1.5, 1.75 など)がずれの主要因です。** DPR = 1.25 のとき、CSSの `1px` は物理 `1.25px` に相当しますが、物理ピクセルは整数しか存在しないため、ブラウザは 1px にするか 2px にするかを決めなければなりません。CSS上の整数pxですら、物理ピクセルの整数境界に乗らないのです。

### 1.4 レイアウト内部単位

ブラウザは内部の計算をfloatではなく固定小数点で行います。丸めの発生位置がエンジンごとに違うため、同じCSSでも結果が変わります。

- **Chrome / Edge (Blink)**: `LayoutUnit` = 1/64 px 単位で計算し、描画時にデバイスピクセルへスナップ
- **Firefox (Gecko)**: app unit = 1/60 px 単位で計算
- **Safari (WebKit)**: 独自のピクセルスナップを実施

「Chromeのズーム110%でだけ再現する」といった、環境依存で再現しづらいバグになるのはこのためです。

## 2. ズームするとpxはどうなるか

「ズーム」と一口に言っても、挙動の異なる3種類があります。混同するとデバッグを誤ります。

### 2.1 ブラウザズーム(Ctrl + `+` / `-`)

**CSSピクセルそのものが拡大縮小されます。**

ズーム110%にすると、CSS `1px` が物理的に1.1倍の大きさになります。その結果、同じ画面幅に入るCSSピクセルの数は減ります。

```
CSSビューポート幅 = 画面のCSS px幅 ÷ (ズーム率 / 100)
```

例: 1366px幅の画面をズーム110%で表示すると、`window.innerWidth` は約 1241.8px になります。

重要なのは次の2点です。

- **`window.innerWidth` が変化する** — レイアウトは新しいビューポート幅で再計算され、メディアクエリも再評価されます
- **`devicePixelRatio` が変化する** — ズーム率が掛け合わされるため、DPR 1 の環境でズーム110%にすると DPR は 1.1 になります

つまりブラウザズームは、実質的に **任意の半端なDPRを人為的に作り出す操作** です。DPR 1 のごく普通のモニタでも、ズームすれば小数DPRの環境を再現できます。このデモでズーム率を変えて試してほしいのはこのためです。

### 2.2 ピンチズーム(visual viewport zoom)

スマートフォンの2本指ピンチや、デスクトップのタッチパッドピンチです。

こちらは **レイアウトを一切再計算しません**。すでに描画済みの結果を拡大表示するだけで、`window.innerWidth` も変わりません。倍率は別のAPIで取得します。

```js
window.visualViewport.scale;  // ピンチズームの倍率
window.visualViewport.width;  // 実際に見えている領域の幅
```

「レイアウトビューポート(layout viewport)」と「ビジュアルビューポート(visual viewport)」の区別がここに対応します。ピンチズームで動くのは後者だけです。したがって **ピンチズームでは1pxずれは新たに発生しません**(既存のずれが拡大されて目立つことはあります)。

### 2.3 OSの表示スケール

Windowsの「拡大縮小とレイアウト 125%」や、macOSの解像度設定です。ブラウザ起動時点で `devicePixelRatio` に反映されます。

ユーザーが意識的に触っていない設定なので、開発者が見落としやすい発生源です。**Windowsノートの既定値が125%や150%であることは珍しくありません。**

### 2.4 CSS `zoom` プロパティ

`zoom: 1.1` は要素単位でのスケーリングです。かつてはIE独自仕様でしたが、現在は標準化され主要ブラウザで動作します。`transform: scale()` と違い、レイアウトに影響を与える(周囲の要素を押しのける)点が異なります。当然、端数の発生源になります。

### 3種類の比較

| | レイアウト再計算 | `innerWidth` | `devicePixelRatio` | 1pxずれの新規発生 |
| --- | --- | --- | --- | --- |
| ブラウザズーム | する | 変わる | 変わる | **する** |
| ピンチズーム | しない | 変わらない | 変わらない | しない |
| OS表示スケール | する | 変わる | 変わる | **する** |
| CSS `zoom` | する | 変わらない | 変わらない | **する** |

## 3. なぜ1pxずれるのか

ここまでを踏まえると、ずれの発生機序は3段階で説明できます。

### 3.1 割り切れない値が生まれる

`700px` を3等分すると `233.333...px` です。相対指定(`%`, `fr`, `flex`, `vw`)を使う限り、こうした無限小数は日常的に発生します。

### 3.2 描画時に整数のデバイスピクセルへ丸められる

物理ピクセルは整数しかないため、最終的にどこかで丸めが起きます。DPRが小数だと、CSS上できれいな値でも丸めが必要になります。

### 3.3 丸めた値の合計は元の値と一致しない

これが本質です。

```
233.333px を3つ並べる
  → 各列を個別に 234px へ丸める
  → 合計 702px(元の 700px より +2px)
```

要素ごとに独立して丸めると、誤差が累積して親要素の幅を超えます。逆に切り捨てられれば要素間に隙間(hairline gap)が生まれます。

親要素からはみ出した分は `overflow-x: auto` の枠内でスクロール可能領域として扱われ、**横スクロールバーが出現します**。これがこのデモで観察できる現象です。

なお、モダンなレイアウト手法(`fr` や `flex`)ではブラウザが余りを内部で分配するため、通常は合計が親を超えないよう調整されます。それでもズーム率とDPRの組み合わせ次第で、スナップの結果が枠を1px超えることがあります。

## 4. このデモの構成

```
ScrollContainer   width: 700px; overflow-x: auto; border: 1px solid #ccc;
└─ ScrollContents width: 100%; display: grid;
                  grid-template-columns: 1fr 1fr 1fr;
   ├─ コンテンツ１  (赤系)
   ├─ コンテンツ２  (緑系)
   └─ コンテンツ３  (青系)
```

`700 ÷ 3 = 233.333...` という割り切れない分割を、外枠に対してぴったり収める必要がある構造です。3色に塗り分けてあるので、列の境界に1pxの隙間や重なりが出た場合も目視で確認できます。

ヘッダーのデモ切替(デモ１/２/３)のうち、現在実装済みなのはデモ１のみです。

### 観察の手順

1. `pnpm run dev` で起動する
2. `Ctrl` + `+` / `-` でブラウザズームを 80 / 90 / 100 / 110 / 125 / 150 / 175% と変えていく
3. 枠の下に横スクロールバーが出たり消えたりするのを確認する
4. コンソールで数値を確認する

```js
// 現在のDPR(ズーム率が掛かった値)
window.devicePixelRatio;

// 枠の要素を取得して、はみ出しを数値で見る
const el = document.querySelector('[class*="scroll-container"]');
el.scrollWidth - el.clientWidth;  // 0 より大きければはみ出している

// 実際の描画幅(小数を含む)
el.getBoundingClientRect().width;
[...el.firstElementChild.children].map(c => c.getBoundingClientRect().width);
```

各列の幅を足しても親の幅にならない、という状況が数値で見えるはずです。

> OSの表示スケールが125%や150%の環境では、ズーム100%の時点ですでにずれが出ることがあります。再現条件はブラウザとDPRの組み合わせで変わるため、複数の環境で試すと理解が深まります。

## 5. 典型的な症状

- 意図しない横スクロールバーが特定のズーム率でだけ出る(**このデモが再現するケース**)
- 隣接する要素の間に1pxの隙間や線が見える(背景色が透ける)
- 1pxのborderが太く見えたり、消えたり、にじんだりする
- 画像をタイル状に並べると継ぎ目に線が入る
- `transform: scale()` した要素の境界がぼやける
- スティッキーヘッダーの下端に1pxの線が見え隠れする
- `100vw` がスクロールバー幅を含むため、縦スクロールバーがあると横に十数pxあふれる(1pxずれとよく混同される **別問題**)

---

## 6. 対策

### 6.1 レイアウト設計で誤差を出さない

- 幅を個別に計算して並べるのではなく、`flex: 1` やCSS Gridの `fr` にブラウザ側で分配させる。余りを内部で処理するため、合計が親を超えにくい
- `width: 33.33%` を3つ並べるより `grid-template-columns: repeat(3, 1fr)` を使う
- `box-sizing: border-box` を全体に適用し、border/padding分の加算誤差をなくす
- `gap` を使い、`margin` の相殺や加算による誤差を避ける

### 6.2 はみ出し・隙間への対処

- ルート付近での `overflow-x: hidden` は最後の手段。原因の特定を妨げるため、まず誤差の発生源を潰す
- 隙間対策の `margin: -1px` や幅の `+1px` は、別のDPR環境で逆側にずれるため避ける
- タイル画像の継ぎ目には、要素をわずかに重ねるか、1枚のスプライトにまとめる
- 背景が透けて見える隙間は、親要素に同じ背景色を敷けば実害を消せる

### 6.3 描画のにじみへの対処

- アニメーションや `transform` の移動量は整数pxに丸める(`translate(10.5px, 0)` → `translate(11px, 0)`)
- 高DPI環境の細い線には `transform: scaleY(0.5)` を使うhairline手法や、`0.5px` 指定(対応ブラウザのみ)を検討する
- `border` の代わりに `box-shadow: 0 0 0 1px` を使うと、レイアウトに影響せずスナップ挙動を変えられる場合がある

### 6.4 検証方法

- ブラウザズームを 80 / 90 / 110 / 125 / 150 / 175% に変えて症状の有無を見る(このデモの操作そのもの)
- `window.devicePixelRatio` を確認し、小数DPRになっているかを把握する
- `document.documentElement.scrollWidth > clientWidth` ではみ出しを数値で捉える
- `getBoundingClientRect()` は小数を返すため、レイアウト計算値と実描画のずれの調査に使える
- DevToolsのデバイスエミュレーションで任意のDPRを設定し、再現条件を絞り込む
